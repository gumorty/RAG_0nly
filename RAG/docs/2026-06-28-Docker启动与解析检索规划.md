## 当前容器职责

`rag-*` 是管理系统：

- `rag-frontend-1`：知识库问答前端。
- `rag-api-1`：FastAPI 管理后端，负责账号、知识库、会话、模型路由、审计、RAGFlow 调度。
- `rag-postgres-1`：保存用户、知识库映射、文档元数据、会话、答案、引用、检索 trace。
- `rag-redis-1`：缓存和异步状态基础设施。
- `rag-minio-1`：保存管理系统侧上传原文备份。

`docker-*` 是 RAGFlow 引擎：

- `docker-ragflow-gpu-1`：RAGFlow 主服务。
- `docker-es01-1`：Elasticsearch，保存 chunk、稀疏/关键词字段、向量等检索索引。
- `docker-mysql-1`：RAGFlow 元数据。
- `docker-minio-1`：RAGFlow 文件存储。
- `docker-redis-1`：RAGFlow 缓存/队列。

两套 compose 通过 Docker 网络 `docker_ragflow` 打通。管理系统容器内访问 RAGFlow 使用：

```text
http://ragflow-gpu:9380/api/v1
```

## 当前文档处理链路

1. 用户在前端创建知识库。
2. 后端创建或复用 RAGFlow dataset，并把 `ragflow_dataset_id` 写入本地知识库元数据。
3. 用户上传文件、网页或 ZIP。
4. 后端将原始文件保存到本地 MinIO，便于审计和后续复查。
5. 后端把文件提交给 RAGFlow dataset documents API。
6. 对 Excel、CSV、HTML、PPTX 等格式，本项目会先做 RAGFlow 友好的格式标准化，再交给 RAGFlow。
7. RAGFlow 执行 DeepDoc/解析器、chunk、Embedding、索引写入。
8. 后端同步 RAGFlow 文档状态和 chunk 数，在前端展示“解析中/可检索/失败”。
9. 用户提问时，后端调用 RAGFlow retrieval 获取证据。
10. 后端按本地 ACL 过滤证据，做表格证据可读化和问题相关行聚焦。
11. 后端调用当前启用的 Chat 模型生成最终答案，并保存 answer、citation、evidence_score、retrieval_trace。

## PDF、图片和扫描件当前如何处理

当前 PDF 主力依赖 RAGFlow 的 DeepDoc。RAGFlow 官方文档说明，PDF parser 可以选择 DeepDoc、Naive、MinerU、Docling、OpenDataLoader 或第三方视觉模型；DeepDoc 默认做 OCR、表格结构识别 TSR、文档布局识别 DLR。来源：https://ragflow.io/docs/select_pdf_parser

这意味着：

- 可复制文本 PDF：RAGFlow 可走更轻的文本解析/分块。
- 版式复杂 PDF：DeepDoc 负责 OCR、布局、表格结构识别。
- 扫描件/图片型 PDF：依赖 OCR 和版面模型，质量取决于图像清晰度、表格线、旋转、页眉页脚等因素。
- 图片、扫描件、多列表格、科学公式：属于当前最需要增强评估和解析路由的区域。

## 是否需要引入 MinerU

结论：需要，但不建议立刻把所有文档强制切到 MinerU。更合理的是做“解析引擎路由”。

MinerU 官方说明它支持 PDF、图片、DOCX、PPTX、XLSX，输出 Markdown/JSON，能够移除页眉页脚、保持阅读顺序、提取表格/图片/公式、检测扫描 PDF 和乱码 PDF，并支持 CLI、FastAPI、Gradio、本地多服务部署。来源：https://opendatalab.github.io/MinerU/

RAGFlow 从 v0.22.0 起已经把 MinerU 作为可选 PDF parser，并且 RAGFlow 只作为 MinerU API 的远端客户端调用。来源：https://ragflow.io/docs/select_pdf_parser

建议策略：

- 普通 Word、Markdown、纯文本 PDF：继续走 RAGFlow 默认解析。
- 政策表格、扫描件、多列表格、论文/公式/图片密集 PDF：走 MinerU。
- 解析失败、chunk 数异常低、引用片段不可读：自动进入 MinerU 重解析候选队列。
- 前端允许在知识库或文档级别选择解析策略：`自动`、`DeepDoc`、`MinerU`、`Naive`。

## 当前检索如何做

RAGFlow 的 AI Search 文档说明，其检索是关键词相似度和向量相似度加权的 hybrid search。来源：https://ragflow.io/docs/ai_search

本项目当前使用 RAGFlow `/retrieval`，并在后端做了动态检索参数：

- `balanced`：普通问题，默认混合检索。
- `table_exact`：政策表格、金额、地区、年份、上浮标准等问题，扩大候选窗口，降低阈值，提高关键词侧权重。
- `semantic_broad`：总结、概括、进展、风险等口语化宽泛问题，扩大语义窗口，提高向量侧权重。

如果配置 `RAGFLOW_RERANKER_MODEL`，后端会把 `rerank_id` 传给 RAGFlow retrieval。Reranker 的价值在于从较大的候选集合中重新排序，减少“看起来相似但不是最佳证据”的 chunk 混入。Haystack 的文档也建议 hybrid retrieval 后接 ranker/reranker，并用 Recall、MRR、NDCG 评估排序质量。来源：https://haystack.deepset.ai/tutorials/33_hybrid_retrieval 和 https://haystack.deepset.ai/blog/optimize-rag-with-nvidia-nemo

## 对模糊口语问题的处理

当前已经有：

- 基于会话历史的 query rewrite。
- RAGFlow hybrid retrieval。
- 动态检索 profile。
- 表格证据聚焦与相邻行防串扰 guardrail。
- 引用片段可读化。

仍需增强：

- Query decomposition：把“总结进展、风险和下一步”拆成多个子查询。
- 多路召回：原问题、改写问题、关键词抽取问题、文档标题/摘要索引同时召回。
- Cross-document reranker：跨文档排序，避免某个文档因关键词密集独占上下文。
- 文档/章节/段落三层索引：先定位文档和章节，再进入 chunk 级证据。
- 证据充足性判定：没有明确证据时必须拒答或说明缺口，不能用模型常识补。
