# 2026-06-28 修改后代码检查与启动脚本

## 本次已检查的修改策略

当前改动方向是正确的，核心目标是提升“复杂文档解析质量”和“表格问答准确性”：

1. `pdf_probe.py`：新增 PDF 文本层预检，用于判断 PDF 是否更像扫描件。
2. `mineru.py`：MinerU 增加 `auto|always|never` OCR 模式，PDF 默认自动判断，图片默认 OCR。
3. `mineru.py`：MinerU 上传、轮询、zip 下载和解压异常已包装成 `MinerUError`，便于后续 fallback。
4. `table_index.py`：新增 Markdown/HTML 表格的行级事实索引，将表格行转成更容易召回的 `字段=值` 文本。
5. `parser_router.py`：MinerU 成功后会把表格行级索引追加到送入 RAGFlow 的 Markdown。
6. `chat.py`：表格类问题会对行级索引和相关行做轻量加权，并在证据聚焦阶段优先保留相关表格行。

## 本次补齐的缺口

原实现只有 MinerU 成功时才追加表格行级索引。如果 MinerU 超时、失败、文件不走 MinerU，或者普通 Excel/CSV/HTML/PPT 归一化为 Markdown，表格增强就不会进入 RAGFlow。

本次已把表格索引改成统一 Markdown 后处理：

- MinerU 成功：追加表格行级索引。
- MinerU 失败后 fallback 到本地归一化：如果结果是 Markdown，也追加表格行级索引。
- 普通归一化链路：如果结果是 Markdown，也追加表格行级索引。

对应文件：

- `backend/app/services/parser_router.py`
- `backend/tests/test_parser_router.py`

## 当前仍然不足的地方

1. 历史已上传文档不会自动变好。
   这些文档已经在 RAGFlow 里完成过解析和索引，除非重新解析/重建索引，否则不会使用新的 MinerU OCR 和表格行级索引。

2. 现有重新索引能力还需要升级。
   理想做法是：从 MinIO 读取原始文件，重新执行 `prepare_for_ragflow`，删除旧 RAGFlow 文档，再上传新解析结果并重新 parse。否则旧文档仍可能沿用旧的 DeepDoc 结果。

3. 表格结构恢复仍然不够企业级。
   当前 `table_index.py` 能处理普通 Markdown 表和简单 HTML 表，但对复杂 PDF 表格中的 `rowspan/colspan`、跨页表头、合并单元格、省份行续写，还需要更强的结构修复。

4. 真实 PDF 回归集还不够。
   需要把 `docs` 里的差旅费 PDF、带表格的 Excel/PPT、扫描 PDF 建成固定评测集，验证“原文抽取 -> 切块 -> 检索 -> 回答 -> 引用定位”的每一步。

5. 前端还需要展示解析链路状态。
   建议展示每个文档的解析引擎、OCR 是否启用、表格行索引行数、解析质量分、重建索引按钮，让用户知道文档到底是否按新链路入库。

## 启动与开发重启脚本

新增脚本：

```powershell
scripts\dev-restart.ps1
```

常用方式：

```powershell
cd D:\Researching\LLMStart\RAG

# 后端代码变更后
powershell -ExecutionPolicy Bypass -File scripts\dev-restart.ps1 -Service api

# 前端代码变更后
powershell -ExecutionPolicy Bypass -File scripts\dev-restart.ps1 -Service frontend

# 前后端都变更后
powershell -ExecutionPolicy Bypass -File scripts\dev-restart.ps1 -Service all

# 完整无缓存重建
powershell -ExecutionPolicy Bypass -File scripts\dev-restart.ps1 -Service all -NoCache

# 同时运行解析相关后端测试
powershell -ExecutionPolicy Bypass -File scripts\dev-restart.ps1 -Service all -RunTests
```

脚本会执行：

1. 检查 Docker 是否运行。
2. 启动 RAGFlow 官方 compose 栈。
3. 按参数重建 `api` 或 `frontend` 镜像。
4. 启动管理系统的 Postgres、Redis、MinIO、API、Frontend。
5. 可选运行解析相关后端测试。
6. 检查 `http://localhost:8010/api/health` 和 `http://localhost:14070` 是否可访问。
7. 如果启动失败，自动输出 API 和前端最近日志。
