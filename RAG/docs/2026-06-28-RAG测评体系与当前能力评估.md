# 2026-06-28 RAG 测评体系与当前能力评估

## 本次问题结论

`P020241210548865982463.pdf` 出现“0 个分块”不是文档没有被解析或没有入库。

真实状态：

- MinerU 解析成功：`parser_engine=mineru_precise`
- 解析质量分：`1.0`
- MinerU 输出字符数：`38419`
- 表格行级索引：`3` 张表、`30` 行
- RAGFlow 生成分块：`48`
- RAGFlow token 数：`21986`

根因是后端同步 bug：RAGFlow `DONE` 后，本地只更新了 `status=ready`，没有把最终 `chunk_count/token_count/progress` 回写到 `metadata.analysis`。因此前端顶部和文档卡片显示 0，但回答仍可用，因为实际检索和回答走的是 RAGFlow 里的索引。

已修复：

- `/collections/{id}/quality` 也会同步 RAGFlow 文档状态。
- RAGFlow `DONE/FAILED/RUNNING` 都会回写 `ragflow_status` 和 `analysis`。

## 当前链路能力

### 解析

当前策略：

- PDF、图片、Word、PPT、Excel 等复杂文档优先走 MinerU。
- PDF 会先做文本层预检，疑似扫描件自动启用 OCR。
- MinerU 失败后 fallback 到本地归一化或 RAGFlow DeepDoc。
- CSV/XLSX/HTML/PPTX 可本地归一化为 Markdown 再交给 RAGFlow。

不足：

- 复杂 PDF 表格的 `rowspan/colspan`、跨页表头、合并单元格仍需要更强结构恢复。
- 历史旧文档不会自动重新享受新解析链路，需要做“从 MinIO 原文件重新解析并重建 RAGFlow 索引”的功能。

### 清洗

当前策略：

- MinerU 输出 Markdown。
- 本地归一化会把 Office/HTML/CSV 转成 Markdown。
- 对乱码、空文本、扫描件有质量评分提示。

不足：

- 缺少统一清洗流水线版本号。
- 缺少清洗前后 diff、低质量片段剔除、页眉页脚/目录/噪声块识别。

### 切片与入库

当前策略：

- 主链路把切片、embedding、索引交给 RAGFlow。
- 本系统只保存原文对象、文档元数据、RAGFlow 文档状态和解析质量。
- 表格会额外生成行级检索索引，增强表格问答。

不足：

- 本地没有保存 RAGFlow chunk 明细，所以无法直接做 chunk 级人工审阅、局部重切片、chunk 级标注。
- 前端还需要增加“查看 RAGFlow 分块/引用定位/原文页码”的治理入口。

### 检索

当前方法：

- RAGFlow Elasticsearch 路径使用向量检索 + 全文词项分数融合。
- 支持可选 reranker。
- 本系统外层会生成多查询计划，最多 4 个 query variant 合并。
- 表格问题会对表格行级索引和问题实体做轻量重排。
- 引用返回后会做可读性清洗和证据评分。

不足：

- 多路召回还不够体系化，当前主要是 RAGFlow 混合检索 + query variants，不是完整的“标题召回、章节召回、表格行召回、关键词召回、语义召回、同义词扩展、问题意图路由”的多通道框架。
- reranker 现在是可选配置，需要为企业场景固定评估不同 reranker 的收益。
- 模糊口语问题目前依赖 query rewrite 和 RAGFlow 混合检索，缺少独立意图识别、实体规范化、同义词词表和领域词库。

## 上下文与记忆

当前设计：

- 会话问答会落库到 `answers`，同一个 session 可拉取历史消息。
- 前端展示历史时会请求 `limit=1000`。
- 但真正发送给模型的上下文只取最近 8 条消息，每条最多 1800 字。

结论：

如果一个会话聊了一百多轮，模型不一定能回忆很早之前的内容。当前系统是“短上下文对话”，不是完整长期记忆系统。

建议升级为三层记忆：

1. 短期窗口：最近 8-20 轮，直接进入 prompt。
2. 会话摘要：每 10-20 轮生成滚动摘要，保留目标、约束、关键结论、未解决问题。
3. 语义记忆：把历史问答切成记忆片段，按 session_id 和 collection_id 建索引，用户问“刚才/前面/我们之前说过什么”时先检索会话记忆，再合并知识库证据。

## 企业级测评指标设计

### 1. 解析质量

- `parse_success_rate`：解析成功率。
- `ocr_needed_accuracy`：扫描件/OCR 识别判断准确率。
- `text_extraction_coverage`：抽取文本覆盖率。
- `table_structure_score`：表格结构恢复分。
- `garbled_rate`：乱码率。
- `metadata_completeness`：标题、页码、章节、表格、图片说明等元数据完整度。

### 2. 切片质量

- `chunk_count`：分块数。
- `avg_chunk_tokens`：平均 chunk token 数。
- `chunk_overlap_rate`：重叠比例。
- `orphan_chunk_rate`：缺失标题/来源/页码的 chunk 比例。
- `table_row_index_coverage`：表格行级索引覆盖率。
- `boundary_quality`：切片边界是否切断表格行、标题、段落。

### 3. 检索质量

- `recall@k`：标准答案相关 chunk 是否进入 top-k。
- `precision@k`：top-k 中相关 chunk 占比。
- `mrr`：第一个相关 chunk 的倒数排名。
- `ndcg@k`：多相关证据排序质量。
- `citation_readability_rate`：引用片段可读率。
- `table_query_accuracy`：表格类问题检索准确率。
- `ambiguous_query_recall`：模糊/口语问题召回率。

### 4. 生成质量

- `faithfulness`：答案是否完全被证据支撑。
- `answer_correctness`：答案与参考答案匹配度。
- `unsupported_claim_rate`：无证据断言比例。
- `citation_coverage`：关键结论是否都有引用。
- `duplicate_line_count`：重复输出行数。
- `refusal_accuracy`：证据不足时是否正确拒答。

### 5. 记忆质量

- `short_context_accuracy`：最近几轮上下文记忆准确率。
- `long_session_recall`：几十轮以前信息召回率。
- `session_isolation`：不同会话记忆是否隔离。
- `memory_conflict_rate`：历史记忆与文档证据冲突率。

### 6. 性能与稳定性

- `ingest_latency_p50/p95`：文档入库耗时。
- `retrieval_latency_p50/p95`：检索耗时。
- `answer_latency_p50/p95`：回答耗时。
- `cost_per_document`：单文档解析/embedding/生成成本。
- `failure_rate_by_file_type`：按文件类型统计失败率。

## 下一阶段实现建议

1. 先把 `evalsets` 升级成通用测评集格式，支持解析、检索、问答、记忆四类 case。
2. 后端增加 `evaluation_runs/evaluation_results` 本地表，保存每次测评快照。
3. 对接 RAGFlow retrieval，跑 `recall@k/mrr/ndcg`。
4. 增加 LLM-as-judge 但不能单独依赖它，必须同时保留规则指标。
5. 为 `docs` 目录下真实 PDF 建一个固定基准集，尤其覆盖政策表格、扫描件、论文、PPT、Excel。
6. 前端增加“测评中心”：选择知识库、选择测评集、运行、查看失败样例、跳转引用原文。
